### 4.3 ЛОВУШКА, на которой легко потерять работу

Наивная проверка `git status --short` внутри рабочей копии показывает неотслеживаемые
файлы **родительского репозитория** — с путями вида `?? ../../../.beads/`. 2026-08-12
из-за этого 13 копий из 23 выглядели «грязными», хотя своей несохранённой работы в них
не было.

Правильная проверка — ограничить область самой копией:

```bash
git -C "$worktree" status --short -- .
```

Ошибка работает в обе стороны: можно и пропустить пустую копию, и — что хуже — принять
за пустую ту, где есть работа.

воспроизвелась. Это ничего не отменяет — правило и тест на него обязательны (§8.2).
Проверять надо тестом на подготовленном репозитории, а не наличием расхождения
в текущем состоянии диска.

## 5. Правила удаления

### 5.1 Каталоги заданий

Удалять `~/.claude/jobs/<id>/`, если выполнено ЛЮБОЕ из:

1. возраст (по времени последнего изменения) больше 14 дней;
2. размер больше 1 ГБ И возраст больше 2 дней.

И при этом НЕ выполнено ни одно условие защиты из §5.3.

### 5.2 Рабочие копии

Удалять копию, только если выполнены ВСЕ условия:

1. нет несохранённых изменений — проверка **с ограничением области**, см. §4.3;
2. нет коммитов, которых нет в основной ветке (`git rev-list --count <main>..<ветка>`
   даёт 0);
3. ветка копии слита в основную;
4. копия не заблокирована — см. §5.3.

Иначе — пропустить и записать в журнал причину пропуска.

Удалять через `git worktree remove` (не `rm -rf`), чтобы репозиторий не остался с
битой записью о копии. После удаления копий выполнить `git worktree prune`.

Основную ветку определяй у самого репозитория, а не хардкодом: в проверенных
репозиториях это `master`, но полагаться на это нельзя.

### 5.3 Защита живого — механизмы проверены, бери готовые

Прошлая редакция оставляла способ проверки на твоё усмотрение. Теперь он выяснен —
вот что проверено на реальном состоянии, с оговорками.

**Для рабочих копий — надёжный сигнал.** `git worktree list --porcelain` выдаёт для
заблокированной копии строку вида:

```
locked claude session do-feature-4qq2-psof (pid 1580358 start 14363310)
```

Идентификатор процесса берётся прямо оттуда, и он проверяемо живой (процесс работает
2 дня 23 часа). Правило: строка блокировки есть → копию **не трогать**, независимо от
того, жив ли указанный процесс. Живой процесс — тем более. Мёртвый процесс в блокировке
(«застрявшая блокировка») — это отдельный случай, который **в область этого задания не
входит**: сообщи о нём в журнал и оставь человеку.

**Для каталогов заданий надёжного сигнала нет — и это надо учесть честно.** Проверены
три способа, каждый со своей дырой:

1. Поле `state` в `state.json` принимает значения `working`, `done`, `blocked`.
   Дыра: у трёх каталогов файла нет вовсе.
2. Идентификатора процесса внутри `state.json` **нет** — во всех 13 каталогах поле
   отсутствует. Способ «взять pid из файла состояния» не работает, не трать на него время.
3. Совпадение идентификатора задания со строкой запуска живого процесса
   (`pgrep -af "$id"`) — работает, но **не полно**. Контрпример: каталог `58fd0d4a` —
   это живая сессия, из которой писался этот файл, а совпадений по строке запуска
   у неё **ноль**. Один этот способ удалил бы каталог активной сессии.

Поэтому защита строится **из всех сигналов сразу**, и достаточно любого одного, чтобы
каталог не трогать:

1. это каталог текущего запуска — переменная окружения `CLAUDE_JOB_DIR` указывает
   ровно на него (проверено: `/home/bgs/.claude/jobs/58fd0d4a`);
2. `state` в `state.json` не равно `done`;
3. `state.json` отсутствует, а возраст каталога меньше порога из §5.1;
4. есть живой процесс, в строке запуска которого встречается идентификатор задания;
5. возраст по времени последнего изменения меньше 2 дней.

Пункт 5 — последняя сетка, и на практике именно он спасает `489aae77`: задание пишет
в свой каталог, поэтому время изменения всегда свежее.

В отчёте опиши, какой из сигналов сработал для каждого пропущенного каталога.

### 5.4 Кэш сборки Docker — только на `vpn-2`

Решено 2026-08-13. Реализуй **отдельным модулем со своим ключом**, не смешивая с
Claude-уборкой: у них разная область, разный риск и разная цена ошибки. Включён этот
модуль по умолчанию только на `vpn-2`; на ноутбуке — нет (§3.4, §11.1).

Что проверено на месте:

1. Пользователь `bgs` входит в группу `docker` — права суперпользователя не нужны,
   требование §6.3 не нарушается.
2. Оба работающих контейнера подняты две недели назад и здоровы:
   `tg-video-downloader-tg-video-downloader-1` и
   `tg-video-downloader-telegram-bot-api-1`. Очистка кэша сборки их не касается, но
   доказать это в режиме проверки без удаления всё равно обязательно.
3. Команда `docker builder prune` перенаправляется на `docker buildx prune`. У неё
   есть ключ `--force` (не спрашивать подтверждения) — без него в планировщике она
   зависнет на вопросе.

**Ограничения области — обязательны:**

1. Чистить **только кэш сборки**. Образы, тома, сети, контейнеры не трогать. У кэша
   сборки к освобождению 20.7 ГБ; у остального на сервере — почти ничего (образы
   активны на 100%), а риск несравнимо выше.
2. Ключ `--all` **не использовать**.
3. Решить и обосновать в отчёте: чистить кэш целиком или ограничить его размер. У
   команды есть ключи `--filter`, `--max-used-space`, `--reserved-space` и
   `--min-free-space` — они позволяют оставить свежую часть кэша, чтобы следующая
   сборка не собиралась с нуля. Полная очистка даёт больше места, но следующая
   сборка `tg-video-downloader` станет заметно дольше. Открытый вопрос — §11.2.
4. Если Docker на машине не установлен или служба не отвечает — записать в журнал и
   продолжить. Не ошибка.

## 6. Требования к скрипту

1. **Один файл на обе машины.** Никаких «версии для ноутбука» и «версии для сервера».
2. **Режим проверки без удаления обязателен** (ключ вида `--dry-run`).
3. **Не требовать прав суперпользователя.** На `vpn-2` беспарольный `sudo` недоступен —
   проверено, всё задание умещается в права обычного пользователя.
4. **Никаких `rm -rf` по шаблону.** Каждый путь удаления — вычисленный и проверенный.
5. **Отсутствие `~/.claude/jobs/` — штатная ситуация**, код возврата 0 (см. §3.2).
6. **Список копий брать у git, а не обходом каталогов** (см. §4.2).
7. Из инструментов на обеих машинах есть: `bash` 5.2, `git` 2.43, `python3` 3.12.
   Ничего дополнительного не устанавливать.

### 7.2 Расписание — часовые пояса РАЗНЫЕ

Это единственное место, где машины расходятся, и ошибка здесь тихая.

- **Ноутбук:** `Europe/Istanbul`, смещение `+03`.
- **`vpn-2`:** `Etc/UTC`, смещение `+00`. Разница ровно 3 часа.

**Решение по времени, принятое 2026-08-13:**

1. На `vpn-2` уборка запускается в **04:05 по времени сервера** (оно же UTC), что
   соответствует 07:05 по Стамбулу.
2. Общий принцип на будущее: время задаётся **в UTC**, ориентир — 04:01 UTC.

Пункты 1 и 2 расходятся на 4 минуты, и для `vpn-2` неясно, какой из них главнее.
До ответа ставь `vpn-2` на **04:05**, как сказано прямо. Вопрос — §11.3, там же
последствия для ноутбука: «время всюду в UTC» означает, что ноутбук переезжает с
07:00 местного на 07:01 местного, и это надо подтвердить.

Служба cron на `vpn-2` активна, пакет `cron` версии `3.0pl1-184ubuntu2`. Возможность
задать часовой пояс прямо в таблице заданий (`CRON_TZ`) **проверить не удалось** —
страницы руководства на сервере нет. Для `vpn-2` это и не нужно: время сервера уже
UTC, пиши его напрямую. А вот для ноутбука принцип «время всюду в UTC» без этой
переменной не выразить — там cron считает по местному времени, и 04:01 UTC придётся
пересчитывать в 07:01 вручную.

Пересчёт вручную здесь безопасен, и это проверено: в Стамбуле часы не переводят,
смещение `+03` держится круглый год (проверял и январь, и июль 2027 — разницы нет,
переходов в таблице часового пояса на 2026–2028 не значится). То есть 3 часа разницы
между машинами — постоянная величина, а не сезонная. Отсюда: 04:01 UTC — это всегда
07:01 в Стамбуле, без оговорок.

Вариант с таймером systemd на `vpn-2` **не подходит**: для пользователя `bgs`
задержка сеанса (`Linger`) выключена, пользовательские таймеры не переживут выход из
системы. Только cron.

На ноутбуке `crontab -l` сообщает об отсутствии таблицы заданий — её надо создать.

Отдельно: на ноутбуке служба синхронизации времени **выключена**, часы не
синхронизированы (`System clock synchronized: no`, `NTP service: inactive`). На
уборку это не влияет, но упомяни в отчёте — расхождение часов делает любые сравнения
по времени менее надёжными.

## 8. Требования к качеству

1. **Первый запуск — только проверка.** Установку в планировщик делать ТОЛЬКО после
   того, как покажешь вывод `--dry-run` с обеих машин и он окажется осмысленным.
2. **Тесты на логику принятия решения.** Как минимум:
   - копия с несохранённой работой не удаляется;
   - копия с неслитыми коммитами не удаляется;
   - чистая слитая копия удаляется;
   - ловушка §4.3 не даёт ложного результата;
   - заблокированная копия не удаляется;
   - каталог задания с `state` = `working` не удаляется;
   - каталог задания без `state.json` и свежий — не удаляется;
   - каталог, на который указывает `CLAUDE_JOB_DIR`, не удаляется;
   - отсутствие `~/.claude/jobs/` не приводит к ошибке.

   Тесты работают на временных репозиториях, а не на реальных данных.
3. **Мутационная проверка — каждого теста.** Убери из скрипта соответствующую проверку —
   тест обязан покраснеть. Тест, который не краснеет при поломке, не считается
   написанным. В отчёте перечисли, что именно ломал и какой тест на это отреагировал.
4. **Проверка переносимости.** `--dry-run` обязан отработать на `vpn-2`, где нет ни
   каталога заданий, ни рабочих копий, и дать пустой список без единой ошибки.

## 11. Открытые вопросы — нужен ответ человека

Закрыто 2026-08-13: кэш сборки Docker на `vpn-2` чистить (§5.4); время на `vpn-2` —

### 11.1 Чистить ли Docker на ноутбуке — и что именно?

На ноутбуке к освобождению **около 38 ГБ**: образы 24.3 ГБ, кэш сборки 13.3 ГБ, тома
319 МБ. Это почти вдвое больше, чем на сервере, и в тринадцать раз больше всего
Claude-мусора, ради которого писалось задание.

Решение по серверу на ноутбук автоматически не переносится: на сервере активны все
образы, а на ноутбуке из 131 образа активны 9 — то есть основной объём там именно в
неиспользуемых образах, а их удаление рискованнее удаления кэша сборки. Заново
скачивать образы — это трафик и время, тогда как кэш сборки пересобирается локально.

Варианты: не трогать ноутбук вовсе / чистить только кэш сборки (13.3 ГБ, риск
минимальный) / чистить кэш сборки и неиспользуемые образы (37.6 ГБ, риск выше).

**До ответа — не трогать.**

### 11.2 Кэш сборки на `vpn-2` — целиком или с сохранением свежей части?

Полная очистка даёт все 20.7 ГБ, но следующая сборка `tg-video-downloader` пойдёт с
нуля. У команды есть ключи ограничения размера (§5.4, п. 3) — можно оставить,
например, несколько гигабайт свежего кэша и чистить только сверх этого.

Вопрос стоит ежедневного повторения: при ежедневной полной очистке кэш не успевает
накопиться, и смысл ограничения размера теряется. Но если сборки идут редко, полная
очистка каждый день — просто холостая работа.

**До ответа — полная очистка**, как более простое поведение, соответствующее прямому
указанию «кэш на сервере тоже удалять».

### 11.3 04:05 или 04:01 — и переезжает ли ноутбук на UTC?

Указание содержало два времени: 04:05 UTC для `vpn-2` и «в дальнейшем везде 04:01
UTC». Для самого `vpn-2` неясно, какое главнее. Расхождение — 4 минуты, на результат
не влияет, но в таблице планировщика надо написать одно число.

Второй, более важный слой: «везде время UTC» означает, что и ноутбук должен считаться
от UTC. Тогда 04:01 UTC — это 07:01 по местному времени вместо нынешних 07:00.
Подтвердить или оставить ноутбук на 07:00 местного.

**До ответа:** `vpn-2` — 04:05, ноутбук — 07:00 местного.

### 11.4 Остальные потребители места на `vpn-2` — в область или нет?

Обнаружены, но решения нет: `/var/log` — 624 МБ, журнал systemd — 484 МБ, кэш `uv` —
673 МБ. Вместе — около 1.8 ГБ, то есть на порядок меньше кэша сборки.

У журнала systemd есть штатное ограничение по размеру, и настроить его правильнее,
чем чистить скриптом каждый день. Кэш `uv` — ускоритель установки пакетов, его
удаление замедлит следующие установки.

**До ответа — не трогать.**

### 11.5 Заблокированное задание живёт вечно — это дефект правил

Логическая дыра в §5.1 и §5.3, замеченная при перепроверке. Правило удаления говорит
«старше 14 дней — удалить». Правило защиты говорит «состояние не `done` — не трогать».
Задание в состоянии `blocked` под второе правило попадает **навсегда**: сколько бы ему
ни исполнилось дней, защита сработает раньше.

Сейчас таких два — `71136913` и `89e02c7c` (68 МБ), обоим меньше суток, так что вреда
пока нет. Но заблокированное задание — это задание, ждущее ответа человека, и оно
может ждать вечно.

Нужен порог: после скольких дней состояние `blocked` перестаёт защищать. Или отдельное
правило — сообщать о таких в журнал, чтобы человек решал вручную.

**До ответа — защита действует, каталог не удаляется.**

### 11.6 Застрявшая блокировка рабочей копии

Копия защищена строкой блокировки, в которой указан идентификатор процесса. Если
процесс умер, а строка осталась — копия становится неудаляемой навсегда, точно как в
§11.5.

Сейчас единственная заблокированная копия (`do-feature-4qq2-psof`) заблокирована
законно: её процесс жив. Проверять живость процесса скрипт умеет.

Вопрос: снимать ли застрявшую блокировку автоматически, если процесс мёртв, и только
потом применять обычные правила §5.2 — или всегда оставлять человеку.

**До ответа — оставлять человеку, писать в журнал.**

### 11.7 Кто узнает, что уборка сломалась?

На `vpn-2` не установлено ни `sendmail`, ни `mail` — проверено. Значит стандартный
