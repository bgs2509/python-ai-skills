# Централизованное логирование

> **Централизованная** конфигурация — один модуль `core/logging.py` (SSoT, DRY). Каждый модуль использует единую настройку, не создаёт свою. AI-агент из логов восстанавливает полный call stack любого запроса.

---

## Log-Driven Design — 11 принципов

| # | Принцип | Суть |
|---|---------|------|
| 1 | **Уровни логирования** | DEBUG — отладка, INFO — нормальный ход, WARNING — потенциальные проблемы, ERROR — требуют внимания, CRITICAL — система неработоспособна. |
| 2 | **Сквозная идентификация** | request_id (уникальный ID операции), correlation_id (ID от клиента, не меняется), user_id (после аутентификации). Все логи содержат request_id. |
| 3 | **JSON-формат** | В production все логи в JSON. Парсятся автоматически. |
| 4 | **Логирование решений** | При ветвлении бизнес-логики записывать: decision (ACCEPT/REJECT/RETRY/SKIP/FALLBACK), reason, evaluated_conditions, actual_values. |
| 5 | **Переходы состояний** | При смене состояния сущности: entity_type, entity_id, from_state, to_state, reason, valid_next_states. |
| 6 | **Входящие запросы** | Middleware автоматически логирует: method, path, duration_ms, status_code, client_ip, auth_context, error_code. |
| 7 | **Исходящие HTTP-вызовы** | Для каждого внешнего вызова: service, operation, method, endpoint, duration_ms, status_code, error_type, is_retryable. |
| 8 | **Операции с БД** | Для каждой операции: operation, table, query_type, duration_ms, found, entity_id. Медленные запросы — WARNING. |
| 9 | **Контекст при старте** | При запуске приложения: service_name, version, environment, python_version, feature_flags, dependencies. |
| 10 | **ContextVars** | Используй contextvars для пробрасывания request_id и user_id через все слои без явной передачи. |
| 11 | **Антипаттерны** | Запрещено: бесполезные логи ("Entering function"), логирование больших объектов целиком, логирование в цикле, дублирование уже залогированной информации. |

## AI-Readable Logging

> AI-агент, читая ТОЛЬКО логи, на 100% понимает что делает программа — какие функции вызываются, в каком порядке, с какими параметрами и результатами.

| Принцип | Описание |
|---------|----------|
| **Полное покрытие логами** | Каждая функция, метод, класс логирует вход и выход. |
| **Вход функции** | Имя функции, входные параметры (с санитизацией секретов), caller (кто вызвал). |
| **Выход функции** | Результат (тип + краткое описание), длительность выполнения, успех/ошибка. |
| **Lifecycle классов** | Создание экземпляра, инициализация зависимостей, уничтожение. |
| **Поток выполнения** | Из логов можно восстановить полный call stack любого запроса. |
| **Ветвления** | Каждое if/else/match логирует какую ветку выбрало и почему (condition + result). |
| **Циклы** | Начало цикла (ожидаемое количество итераций), завершение (фактическое количество), аномалии (0 итераций, слишком много). |
| **Уровни детализации** | DEBUG — трассировка вызовов, INFO — бизнес-события, WARNING/ERROR — проблемы. |
| **Контекст модуля** | Каждая лог-запись содержит module, class, method — AI может построить карту вызовов. |
| **Машиночитаемый формат** | JSON с фиксированной схемой полей. AI парсит без угадывания. |
| **Корреляция** | request_id + span_id для восстановления дерева вызовов в рамках одного запроса. |
| **Самодокументирование** | Логи заменяют отсутствующую документацию — AI читает логи вместо чтения кода. |

## Structured Logging (structlog)

- Единая конфигурация в `core/logging.py` (SSoT)
- structlog как основная библиотека
- JSON формат в production, human-readable в development
- Процессоры: add_log_level, timestamper, StackInfoRenderer
- Интеграция с stdlib logging для сторонних библиотек

---

## Correlation ID

- `request_id` — генерируется на входе (middleware), уникален для каждого запроса
- `correlation_id` — приходит от клиента (заголовок `X-Correlation-ID`), сохраняется через всю цепочку
- `user_id` — добавляется после аутентификации
- Хранение через `contextvars` — доступно во всех слоях без явной передачи (DRY)
- В микросервисах: correlation_id передаётся между сервисами через HTTP-заголовки

## Санитизация (Security)

Секретные поля автоматически маскируются в логах как `***REDACTED***`:

- password, passwd
- token, access_token, refresh_token
- secret, api_key, api_secret
- authorization
- credit_card, card_number
- ssn, social_security

Санитизация реализуется как процессор structlog — в одном месте (SSoT, DRY).

## Централизованное логирование по слоям (DRY)

| Слой | Как логировать | Кто логирует |
|------|---------------|-------------|
| Входящие HTTP | Middleware (автоматически) | RequestLoggingMiddleware |
| Исходящие HTTP | Базовый HTTP-клиент (автоматически) | Единый клиент — см. skill `http-clients` (http-clients/reference.md) |
| Операции с БД | Repository базовый класс (автоматически) | BaseRepository |
| Бизнес-логика | Явно в Application Services | Разработчик |
| Ошибки | Централизованный handler (автоматически) | Exception handler — см. skill `error-handling` (error-handling/reference.md) |

**Запрет (DRY)**: не дублировать логирование, которое уже выполняется автоматически (middleware, базовый клиент, handler).

## Запреты (blocker)

| Антипаттерн | Почему плохо |
|-------------|-------------|
| Бесполезные логи ("Entering function", "Done") | Шум, не несут информации |
| Логирование больших объектов целиком | Переполнение логов, замедление |
| Логирование в цикле | N записей вместо одной (начало + итог) |
| Дублирование уже залогированной информации | Нарушение DRY |
| Каждый модуль настраивает логирование по-своему | Нарушение SSoT |
| `print()` вместо `logger` | Не структурировано, не парсится |
| Логирование секретных данных | Security violation |
