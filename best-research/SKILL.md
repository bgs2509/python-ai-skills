# /best-research — Движок разбора одной точки решения

> Единое ядро (SSoT) семьи `best-*`: изучить состояние → раскопать настоящее намерение → проверить качество → дать варианты + % → рекомендовать.
> `best-approach`, `best-rank`, `best-questions` — тонкие обёртки, различающиеся **только входом**; всю работу делает этот движок.

## Вход

Одна **точка решения**: идея, вопрос, подход или дилемма — со списком готовых вариантов ИЛИ без него. Если вход не передан — спроси: «Какую точку решения разбираем?».

## Алгоритм

### 0. Структурированное мышление
Весь разбор (шаги 1–5) веди через `mcp__sequential-thinking__sequentialthinking` — один сеанс от исследования до финальной рекомендации.

### 1. Исследование контекста (обязательно)
- **Код:** прочитай CLAUDE.md (project/user/global), pyproject.toml, структуру проекта, релевантные файлы — реальные паттерны, зависимости, уже существующие решения. *(НЕ читать `.env`, `*.pem`, `*.key` — только `.env.example`.)*
- **Готовое решение:** проверь, нет ли уже реализованного в проекте (DRY).
- **Документация:** Context7 (`resolve-library-id` → `query-docs`) для КАЖДОЙ библиотеки/фреймворка из вариантов. Версии — сверить с `uv.lock` (строго `==`).
- **Интернет:** `WebSearch` — актуальные подходы, известные подводные камни, свежие альтернативы.

### 2. Мета-анализ (раскопать настоящее намерение)
На основе исследования, не буквальной формулировки:
1. **Настоящая цель** — какую задачу пользователь реально решает.
2. **Что хотел, но не сформулировал** — невысказанные требования из контекста.
3. **Ошибочные предположения** — что пользователь считает верным, но код/доки/практика говорят иначе.
4. **Слепые зоны** — edge cases, эксплуатация, миграция, тесты, безопасность, стоимость поддержки.
5. **Уточняющие вопросы** — 3–5, привязанных к конкретике проекта (не generic). Если ответы могут сдвинуть рекомендацию — дождись их перед фиксацией.

### 3. Проверка по 17 принципам качества (`_code-quality`)
**Basic (1-7):** DRY, KISS (≤50 строк/функция, вложенность ≤4), YAGNI, SoC, SSoT, CoC, Security
**SOLID (8-12):** SRP (класс ≤500 строк), OCP, LSP, ISP, DIP
**Additional (13-17):** LoD (без цепочек `a.b.c.d`), Fail Fast, Explicit > Implicit, Composition > Inheritance (глубина ≤2-3), Testability

Для каждого варианта: какие принципы **усиливает**, какие **нарушает/ослабляет** — со ссылкой на конкретный принцип, не generic фразы.

**Red Flags** (БЛОКЕР, отметить явно): `except: pass`, God class >500 строк, magic numbers, copy-paste, ненужные `*args/**kwargs`, bypass хуков/проверок как «решение». Подробно: `_code-quality/reference/quality-cascade.md`.

### 4. Варианты
- Если список вариантов **дан** — не теряй ни один, даже слабый (с причиной «почему нет»).
- Если выявлены best-practice решения, которых в списке **нет** — добавь как новые, пометь «**[добавлено]**». Не раздувай ради количества — только реально конкурентоспособное.
- Если списка нет — формируй варианты сам, адекватно сложности: простая задача → 2–3, средняя → 3–4, сложная → 4–5.
- Pros/Cons — честные, со ссылкой на принципы качества.

### 5. Рекомендация
Подай по формату `/best-recommend`: **проценты уверенности + объяснение как джуну + источник к каждому % + честный флаг гипотезы при сомнении**. Шкала: 85–100% — сильный фаворит; 50–84% — рабочий с оговорками; 20–49% — слабый/ситуативный; 0–19% — почти нет (но оставить с причиной).

## Правила

1. **Исследование обязательно** — код + Context7 + WebSearch + CLAUDE.md. Без этого разбор недостоверен.
2. **Объективность** — Pros/Cons и проценты честные, не подгонять под желаемый вывод.
3. **Контекст проекта** — стек, зависимости, паттерны, тип проекта (dev/life), профиль юзера.
4. **СТОП перед действием** — ничего не реализовывать до явного выбора пользователя.
5. **Адаптация формата** — Telegram: без таблиц, короткие блоки; CLI: таблицы допустимы.
6. **Адаптация языка** — по профилю пользователя (CLAUDE.md). По умолчанию — русский.
7. **Не применяется к** — подаче уже готовой рекомендации (это `/best-recommend`).

## Роль в семье best-*

- `best-research` = **движок** (research / analysis одной точки решения). Worker: возвращает findings вызывающему, **не** переключает workflow и **не** вызывает process-skills.
- Обёртки переиспользуют этот алгоритм **по ссылке** (следуют спецификации), различаясь только входом:
  - `best-approach` — задача без списка → генерит варианты с нуля, затем этот движок.
  - `best-rank` — готовый список → этот движок + ранжирование по % убыв.
  - `best-questions` — набор вопросов → цикл по движку, СТОП после каждого.
- Формат финальной рекомендации — атом `best-recommend`.

**Обязательно:** Context7 перед любой работой с библиотекой/фреймворком. TDD при последующей реализации (RED → GREEN → REFACTOR).
