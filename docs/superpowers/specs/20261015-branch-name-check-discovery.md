# Discovery: branch names carry the `branch` segment, enforced by one PreToolUse deny hook (python-ai-skills-31d)

## Intent

Every branch name created in any project on this machine must contain the word `branch` as a separate segment, so
that a branch name is never mistaken for a coined term (bd `python-ai-skills-31d`: models invent names like
`worktree-lazy-juggling-lovelace`; the explanation-terms Stop hook flagged such `worktree-*` names as coined terms).
The rule exists since 2026-10-15 as **N-BRANCH** in `claude-home/CLAUDE.md:87`. This feature adds the enforcement
half: a check that denies the model's own branch-creating calls when the name lacks the segment.

Audit of existing branches (acceptance criterion; re-counted 2026-10-15, `git for-each-ref refs/heads/` over the 83
directories with a `.git` under `~/ai-steward/Gena_Beeline_Local`): 97 local branches, 23 of 97 are neither `main` nor
`master`, 0 of 97 contain a `branch` segment, 10 of 97 start with `worktree-` (the Claude Code prefix). The bd
description counted 74 repos and 95 branches the same day (9 non-project `.git` directories and 2 newer branches).

## Constraints - decisions the user already made (bd 31d notes 2026-10-15, final after OQ-3 and OQ-4; not reopened)

1. NO `WorktreeCreate` hook and NO `WorktreeRemove` hook: they never existed and are not added. Reason
   (code.claude.com/docs/en/worktrees): a hook-created worktree loses the built-in removal of subagent worktrees
   without changes and the periodic sweep - "the sweep keeps any worktree without one [marker], including a worktree a
   `WorktreeCreate` hook created". Built-in worktree creation and cleanup stay as they are (OQ-3, user answer 1).
2. ONE new `PreToolUse` hook that DENIES (exit 2, stderr names the correct form `<type>/branch-<slug>`), same style as
   `claude-home/hooks/block-no-verify.sh` (best-approach Q2, user answer 1):
   a. Bash git commands that create a branch without the `branch` segment. Explicit forms: `checkout -b/-B/--orphan`,
      `switch -c/-C/--create/--force-create/--orphan`, `branch <name>`, `worktree add -b/-B`. Implicit new names:
      `git worktree add <path>` without `-b`/`-B`/`--detach` (basename becomes the branch), `git branch -m/-M/-c/-C
      <old> <new>`. ALLOWED: copying an existing remote name (DWIM `git checkout <name>` with `origin/<name>`,
      `--track`) and every non-creating command (`branch -d/-D`, `worktree remove`, `checkout -- <file>`, ...)
      (OQ-4, auto-selected under the global Questions and Numbers threshold).
   b. `EnterWorktree` calls whose `name` lacks the `branch` segment (Claude Code then makes `worktree-<name>`, turning
      `/` into `+`). `EnterWorktree` with `path` (entering an existing worktree) is allowed.
3. N-BRANCH text in `claude-home/CLAUDE.md` (`## Naming`): add `+` to the segment boundaries; state that temporary
   subagent worktree branches Claude Code generates (`worktree-agent-<hex>`) are outside the rule; document the
   override value `N-BRANCH: off`.
4. Override: the hook reads `<git toplevel of input cwd>/AGENTS.md` section `## Naming overrides`; only `N-BRANCH: off`
   disables the check; any other N-BRANCH text keeps the global check and the deny message notes it is not
   machine-readable (best-approach Q4, user answer 1).
5. Existing branches are not renamed and must not trigger anything (`claude-home/CLAUDE.md:87`, last sentence). NOT
   covered: branches a human creates in a terminal, including `claude --worktree <name>` typed by the user.

Constraint check against facts: 1-5 hold (facts below).

## PreToolUse contract (code.claude.com/docs/en/hooks and /tools-reference, fetched 2026-10-15; quotes verbatim)

- Input: "In addition to the common input fields, PreToolUse hooks receive `tool_name`, `tool_input`, and
  `tool_use_id`." Common fields include `cwd`, `permission_mode`, `hook_event_name`; the Bash example carries
  `tool_input.command`.
- Matcher: for `PreToolUse` the matcher filters the "tool name"; "`Bash` matches only the Bash tool; `Edit|Write` and
  `Edit, Write` each match either tool exactly". Tools reference: "The tool names are the exact strings you use in
  permission rules, subagent tool lists, and hook matchers." and "Hook `matcher` fields use bare tool names". So
  `EnterWorktree` is a valid matcher value.
- EnterWorktree (tools reference, tool table): "Creates an isolated git worktree and switches into it. Pass a `path` to
  switch into an existing worktree instead of creating a new one. ... From within a worktree session, or from a
  subagent with a pinned working directory such as `isolation: worktree`, only the `path` form is available". Its
  `tool_input` fields, from the tool definition loaded in this session (Claude Code 2.1.296): `name` - "Optional name
  for a new worktree. Each `/`-separated segment may contain only letters, digits, dots, underscores, and dashes; max
  64 chars total. A random name is generated if not provided. Mutually exclusive with `path`." and `path` - "Path to
  an existing worktree to switch into instead of creating a new one". The docs page names only `path`; `name` is
  verified from the definition, not from the page.
- Decision: "`"deny"` prevents the tool call." "A hook that blocks by exiting 2 routes the same way as `"deny"`:
  Claude sees the stderr message as the denial reason." Precedence: "`deny` > `defer` > `ask` > `allow`". Timeout: "A
  timed-out `command`, `http`, or `mcp_tool` hook doesn't block the tool call ... don't count on a stalled hook to act
  as a gate." Crash: "Non-blocking error, execution continues."
- Subagents: "Hooks from settings files, managed policy settings, and plugins also run inside subagents. When a
  subagent calls a tool, tool events such as `PreToolUse` and `PostToolUse` fire the same configured hooks as in the
  main conversation, and the input carries the `agent_id` and `agent_type` common input fields". The subagent sees the
  stderr and must retry; the orchestrator sees nothing unless the subagent reports it. Backgrounded sessions: no
  sentence on PreToolUse in the hooks page (unverified).
- Bash route: "When Claude runs `git worktree add` through the Bash tool rather than calling `EnterWorktree`, your
  WorktreeCreate hook doesn't run. To inspect or block that command, add a `PreToolUse` hook with the `Bash` matcher."
  Live probe of 2026-10-15 (throw-away repo, logging WorktreeCreate hook, not kept): the worktree `name` reaches Claude
  Code with `/` intact, so the `+` in real branch names (`worktree-feat+branch-gateway-concurrency`) comes from the
  built-in sanitising - hence constraint 3 adds `+`.

## Git commands that create a local branch (git 2.43.0 help pages, quoted 2026-10-15)

Explicit new-name forms (the name is the token after the flag, or the next argument) - DENIED without the segment:
1. `git checkout -b <new-branch>` - "Create a new branch named <new-branch>, start it at <start-point>"; `-B` same
   with reset; `--orphan <new-branch>` - "Create a new orphan branch, named <new-branch>".
2. `git switch -c <new-branch>, --create <new-branch>` - "Create a new branch named <new-branch> starting at
   <start-point>"; `-C`/`--force-create`; `--orphan <new-branch>`.
3. `git branch [--track|--no-track] [-f] [--recurse-submodules] <branchname> [<start-point>]` (SYNOPSIS line 2): the
   first non-option argument is the new name. Non-creating flags: `-d`/`--delete`, `-D`, `-l`/`--list`, `-a`, `-r`,
   `-v`, `--show-current`, `-u`/`--set-upstream-to`, `--unset-upstream`, `--edit-description`, `--merged`,
   `--no-merged`, `--contains`, `--points-at`, `--format`, `--sort`, `--column`, `--color`.
4. `git worktree add [(-b | -B) <new-branch>] <path> [<commit-ish>]` - "With add, create a new branch named
   <new-branch> starting at <commit-ish>"; `--orphan`.

Implicit new-name forms - DENIED without the segment (constraint 2a):
5. `git worktree add <path>` with no `<commit-ish>`, `-b`, `-B` or `--detach`: "the new worktree is associated with a
   branch (call it <branch>) named after $(basename <path>). If <branch> doesn't exist, a new branch based on HEAD is
   automatically created as if -b <branch> was given." The checked name is `basename <path>`.
6. `git branch -m/--move <old> <new>`, `-M`, `-c/--copy <old> <new>`, `-C` ("Move/rename a branch", "Copy a branch"):
   the last argument is the new name; with one argument (`git branch -m <new>`) the current branch is renamed to it.

Copying forms - ALLOWED (the local name copies an existing remote name; constraint 2a):
7. `git checkout <branch>` / `git switch <branch>` / `git worktree add <path> <branch>` when the name exists only on one
   remote: "treat as equivalent to `git checkout -b <branch> --track <remote>/<branch>`" (DWIM); `git checkout --track
   <remote>/<name>` / `-t`: "the name of the new branch will be derived from the remote-tracking branch".

Out of scope by definition (no local branch): `git push origin HEAD:refs/heads/<name>`, `git stash`, tags, `git fetch`.

## Risks and mitigations

1. False positives on non-creating commands (`git branch -d x`, `git branch --list`, `git checkout -- file`,
   `git checkout main`, `git worktree remove`, `git worktree add <path> --detach`, `git push -u origin HEAD`) block
   legitimate work in all 83 repos. Mitigation: FR-5 ALLOWED list in tests; the parser treats only forms 1-6 as creating.
2. False positives from text, not commands: a name inside `-m "..."`, a heredoc body, `echo 'git checkout -b x'`,
   `grep -rn "checkout -b"`. Mitigation: shlex tokens (a quoted string is one token, never a `git` token), the
   pattern's `-m`/`--message` value skip (`block-no-verify.sh:104-108`); the parser stops a segment at `<<`/`<<-`.
3. Compound commands and prefixes: `cd repo && git switch -c x`, `git -C dir checkout -b x`, `VAR=1 git checkout -b x`,
   `command git ...`, `/usr/bin/git ...`, `rtk proxy git ...`. Mitigation: segment split and global-option skip from the
   pattern; a token equal to `git` or ending in `/git` counts as git; `command`, `env`, `nice`, `time`, `rtk proxy`
   prefixes are stripped (test cases).
4. Bypass by construction: `git checkout -b "$NAME"`, `git branch $(cat n)`, `xargs git branch`, a script file. A deny
   hook on command text cannot see runtime values. Accepted: the rule covers the model's typed names.
5. Deny inside a subagent or a background session: the subagent sees the stderr and retries; the orchestrator sees only
   what the subagent reports; a background session is unverified. Accepted; the journal (FR-4) records every deny.
6. Override text that is not `off` (e.g. `N-BRANCH: <type>-branch-<slug>`): the global check stays (constraint 4); a
   project using another compliant form passes anyway because the segment rule is the same; the deny message says the
   override is not machine-readable.
7. Timeout as silent allow: a stalled override lookup (`git rev-parse` on a network mount) turns the gate off without
   notice. Mitigation: NFR-1 (git subprocess only after a creating form is found, `timeout 5`).
8. EnterWorktree `name` with `/` yields `worktree-feat+branch-x`: compliant only because `+` joins the boundary list
   (constraint 3); a reader of the old N-BRANCH text would call it non-compliant. Mitigation: FR-8.
9. Generated subagent branches `worktree-agent-<hex>` (59 of 479 observed names) stay non-compliant by design
   (constraint 3); the explanation-terms Stop hook may still flag them when an answer mentions one. Accepted;
   branch-name recognition stays with bd `python-ai-skills-r1f`. Codex: no hooks run there (NFR-6).
